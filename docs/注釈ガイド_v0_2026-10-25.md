# 注釈ガイド v0（2026-10-25 試作）

予備実験30件（`experiments/pilot-2026-10-25-bunka30/`）に適用し、迷った箇所を記録して v1 に直す。11/5 に固定し、本実験の途中では変えない。注釈は広聴AIを動かす前、または出力を見ずに行う（出力を見てから注釈すると、AIが落としたものに引きずられる）。

## 1. 単位

1コメントから、次の3つの要素を組にした「意見単位」を0個以上取り出す。

| 要素 | 定義 | 例 |
|---|---|---|
| 主張 | 書き手が求めていること、または賛否の立場 | 「無断学習を規制してほしい」 |
| 理由 | その主張を支える根拠。書き手が「なぜなら」「〜ため」で結べるもの | 「創作者の収入が減るため」 |
| 条件 | 主張が成り立つ範囲を限定する語句。「〜なら」「〜の場合は」「〜に限り」「ただし〜」 | 「許諾を得た場合は除く」 |

- 1コメントに複数の主張があれば、主張ごとに別の単位にする。
- 理由がない主張（「反対です」だけ）は、理由欄を「なし」として1単位にする。除外しない。
- 条件がなければ「なし」。
- 書き手の事実認識（「現状は〜だ」）は、主張の理由になっていれば理由に含める。単独の事実の記述は単位にしない。
- 素案の文言修正の指摘（「○ページの△を□に」）は、主張＝修正要求、理由＝書かれていれば記入、として1単位にする。

## 2. 理由群

同じ趣旨の理由を1つの「理由群」にまとめ、短い名前を付ける。名前は原文の語を使い、抽象化しすぎない。

- 「収入が減る」「仕事を奪われる」「創作意欲が下がる」は、書き手が区別しているなら別の群、同じ文脈で並べているなら「創作者の生計・意欲への影響」のように1群にする。迷ったら分けておき、集計時に統合できるよう、親子関係をメモする。
- 条件も同様に「条件群」にまとめる（「許諾があれば可」「商用利用に限る」など）。

## 3. 頻度と「少数」

- 理由群の頻度 ＝ その理由群を含むコメント数 ÷ コメント総数（同じコメント内の反復は1と数える）。
- 本実験では10%以下を「少数」とし、5%・20%でも結論が変わるかを確認する。
- 予備実験30件では件数が少ないので、頻度は参考値。閾値の決定は本実験の100件で行う。

## 4. 記入の約束

- 原文の語をできるだけそのまま使う。言い換えは最小限にする。
- 判断に迷った単位は `confidence` を `low` にし、`note` に理由を書く。v1 を作るときに、この `note` を集めて規則を足す。
- 原文は注釈シートに写さない（投稿者の著作物。シートはコミットする）。`comment-id`（受付番号）で参照する。

## 5. 段階別の判定（AIの出力に対して。注釈が終わってから）

理由群ごとに、各段階の出力に残っているかを次の4値で記録する。

| 値 | 意味 |
|---|---|
| kept | 理由（条件）が意味を変えずに残っている |
| altered | 残っているが、条件が落ちた・賛否が逆になった・語気が変わった |
| absent | 現れない |
| na | 前の段階で既に absent（この段階で新たに消えたのではない） |

- ① 抽出：`relations.csv` でそのコメントから出た意見文（`args.csv`）を見る。
- ② クラスタ：`hierarchical_clusters.csv` で、その理由群の意見文が同じクラスタにまとまったか、別の理由の塊に混ざったか。
- ③ ラベル：`hierarchical_initial_labels.csv` / `hierarchical_merge_labels.csv` の名前と説明文。
- ④ 要約：`hierarchical_overview.txt`。

「その段階で新たに消えた割合」＝ absent ÷（前段階で kept または altered の数）。

## 6. v0 で予想される迷い（v1 で決める）

- 皮肉や反語の主張をどう取るか（kouchou-ai の抽出プロンプト検証でも問題になっている）。
- 「〜すべき」と「〜してほしい」を同じ主張とみなすか。
- 条件が主張そのものになっている文（「許諾制にすべき」は主張か条件か）。
- 長文で主張が10個以上あるコメントの扱い（すべて取るか、上限を設けるか）。
